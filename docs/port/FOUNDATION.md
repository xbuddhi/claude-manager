# Foundation guide for work packages

How the foundation is built and how a work package (WP1-WP10 in `plan.json`) adds its feature. Read
`README.md` in this folder first: the owner's decisions and the decisions below override `plan.json`.

## 1. Setup and checks

New worktree (no `node_modules`, no `dist/`; `generate_context!` needs `../dist`):

```sh
pnpm install --frozen-lockfile
pnpm build
```

On this workstation every cargo command needs (see README for why):

```sh
export RUSTUP_TOOLCHAIN=stable-x86_64-pc-windows-msvc RUSTUP_AUTO_INSTALL=0
```

The full suite, all must pass before a package is done (CI runs the same on Windows and macOS):

| Check | Command (cargo ones in `src-tauri/`) |
| --- | --- |
| Lint (biome) | `pnpm lint` |
| Types | `pnpm typecheck` |
| Unit tests (vitest) | `pnpm test` |
| Frontend build | `pnpm build` |
| Rust format | `cargo fmt --check` |
| Clippy | `cargo clippy --all-targets --locked -- -D warnings` |
| Rust tests (also writes `src/bindings`) | `cargo test --locked` |
| Bindings committed | `git status --porcelain -- src/bindings` is empty after `cargo test` |

`pnpm format` fixes formatting and import order. The machine has 4 cores: a cold cargo build takes about
15 minutes, so run long cargo commands in the background with a 10 minute timeout.

## 2. Architecture as built

```
src-tauri/src/
  lib.rs            builder, plugins, registration markers (modules, init, builder extensions)
  commands.rs       the one generate_handler! list, one marked block per package
  core/             foundation, shared by every feature
    error.rs        AppError {code,message}, AppResult, lock() (poison-proof), blocking()
    paths.rs        home, app dirs, norm(), key() (case rules per OS), same(), is_within()
    fsio.rs         write_atomic()
    env.rs          startup resolution of claude/shell/git/code + PATH, clean_env(), apply_profile(),
                    check_claude_override(), user_name(), env_status / platform_info commands
    spawn.rs        hidden_command() (no console, clean env), output_with_timeout()
    procs.rs        Procs (sysinfo table), parent_chain, descendants_of, kill_trees(pids, grace),
                    Windows job object; start times guard every pid
    profiles.rs     discovery, name, email, resolve_profile() (the gate for webview profile paths),
                    is_session_id(), find_transcript(), refresh(), signed-in hook
    settings.rs     Settings store (lenient read, legacy import, atomic debounced save), commands
    lifecycle.rs    close / quit / reopen / exit, ShutdownHook registry, quit dialog round trip, tray flag
    open_request.rs validated "open this folder" requests from the command line / second launch
    open.rs         open_log_dir, open_url_https (https only)
    terms.rs        TermPids: pids of the app's own terminals
    events.rs       every backend event name, one block per package
    types.rs        shared ts-rs types (Profile, Session, Project, LiveSession, Settings, ...)
    webview.rs      create_main_window(), harden() (navigation guard, no new windows)
  sessions/ (WP1)  pty/ (WP2)  os/ (WP9: menu.rs skeleton)
src/
  main.ts           styles, core start, features
  core/             store, bus, api, settings, profiles, platform, keyboard, commands, views, shell,
                    titlebar, format, paths, dom, icons, motion, log, app (startup, beforeShow)
  ui/               button, segmented, toggle, splitbutton, texttabs, avatar, tooltip, menu, popover,
                    dialog, list, splitter, toast, banner (each with its css)
  features/         one folder per feature; index.ts mounts them
  bindings/         generated by `cargo test`, never edited by hand
  styles/           tokens.css (all colours, light + dark), base.css, shell.css
```

Startup (`core/app.ts`): platform, settings and profiles load in parallel; then title bar, shell, views,
keyboard, `mountFeatures()`; then the first paint waits for `beforeShow()` work (at most 1.5 s); then the
hidden window is shown; then the environment check (the "Claude Code was not found" banner).

Security rules that every command keeps: the webview never names an executable, arguments or environment;
it passes ids (session UUIDs checked with `profiles::is_session_id`), profile folders (checked with
`profiles::resolve_profile`), and folders (checked to exist). Paths to delete must be inside a profile or a
given existing root (`paths::is_within`). Tokens never leave Rust and are never logged. Windows other than
`main` are built through `core::webview::harden`; the webview has no permission to create windows.

## 3. Adding a Rust feature module

1. Create `src-tauri/src/<feature>/mod.rs` (a folder, even when small). It exposes
   `pub fn init(app: &mut tauri::App) -> AppResult<()>` when it needs managed state or background threads.
2. Register it in `lib.rs`, each line directly under your package's marker:
   - `// ---- feature modules ----`: `pub mod <feature>;`
   - `// ---- feature init ----`: `<feature>::init(app)?;`
   - `// ---- builder extensions ----` only for builder-level additions (`let builder = <feature>::attach(builder);`).
3. Commands: `#[tauri::command] pub async fn ...` in your module, listed in your block of `commands.rs`.
   Blocking work goes through `core::error::blocking(|| ...)`; nothing blocking runs on the main thread.
   Return `AppResult<T>`; errors reach the webview as `{code, message}`, and the message is shown to the user.
4. Events: add `pub const NAME: &str = "...";` under your block in `core/events.rs` with a `/// Payload:` line.
5. Types crossing IPC: `#[derive(Serialize, TS)] #[serde(rename_all = "camelCase")] #[ts(export)]` in your
   own module (e.g. `live/types.rs`); `cargo test` writes `src/bindings/<Type>.ts`, which you commit.
   Only types several features share go in `core/types.rs` (add fields, never rename or remove).
   Name clashes: WP2's terminal list type is `PtyInfo` (the frontend tab record is `TermInfo`).
6. Hooks into core:
   - `lifecycle::register(app.handle(), impl ShutdownHook)`: count work that makes quitting ask, and end it on exit
     (use `procs::GRACE_ON_EXIT` there).
   - `terms::register(app.handle(), impl TermPids)`: WP2's terminals (already done for the prototype `Terms`).
   - `open_request::set_parser(app.handle(), parser)`: WP9's argument parser; it is run on this process's own
     arguments at once and on every second launch.
   - `app.state::<profiles::Profiles>().set_signed_in(f)`: WP7's credentials check, fills `Profile.signedIn`.
   - `profiles::refresh(app)`: call when you learn the profile set changed (WP6 after creating one, WP1's
     watcher when a `~/.claude-*` folder appears); it emits `profiles-changed`.
   - `lifecycle::set_tray_present(app)`: WP9, once the tray icon exists.
7. Tests: `#[cfg(test)] mod tests` next to the code; fixtures in `tempfile::tempdir()`; shared fixture files under
   `src-tauri/tests/fixtures/<feature>/`. Pure logic gets pure functions so it can be tested without Tauri
   (see `procs::real_parent`, `open::https_url`). A local HTTP mock (WP7) uses `std::net::TcpListener` on
   `127.0.0.1:0`; no dev-dependency is needed.

Useful core helpers: `paths::key/same/is_within`, `fsio::write_atomic`, `spawn::hidden_command`,
`spawn::output_with_timeout` (timeout = `AppError::Io` of kind `TimedOut`), `env::wait_env()` (resolved
executables and PATH), `env::user_name()`, `procs::Procs` (managed state) and `procs::kill_trees(pids, grace)`,
`settings::get(app)` / `settings::modify(app, f)`.

## 4. Adding a frontend feature

1. Create `src/features/<feature>/index.ts` exporting `mount(): void`, and register it in
   `src/features/index.ts` under your marker in both blocks (import, then mount). The import block is
   exempt from import sorting so the markers stay put.
2. Render only into your shell slot (`#sidebar-slot`, `#tb-search-slot`, `#tb-right-slot`, `#tabstrip-slot`,
   `#picker-root`, `#terminal-root`, `#overlay-root` for menus/popovers/dialogs) or into a view:
   `registerView({ id, title, order, mount(body), headerActions(el), onShow, onHide })` from `core/views.ts`.
3. State: declare your fields by declaration merging in `features/<feature>/state.ts` and give defaults:
   ```ts
   declare module "../../core/store" { interface AppState { gitRepo: string | null } }
   defineState({ gitRepo: null });
   ```
   Read with `store.get()`, write with `store.set(patch)`, react with `store.select(selector, fn)`.
   Core fields (`profiles`, `currentProfile`, `screen`, `settings`, `index`, `live`, `liveCwd`,
   `sidebarSelection`, `terminals`, `activeTerminal`, `view`, `windowFocused`) are documented in `core/store.ts`.
4. Bus events: add yours by merging `interface AppEvents` in `core/bus`; emit with `emit(name, payload)`.
   The core events (`launch`, `terminal:show`, `session:resume`, `refresh:full`, `sidebar:select`,
   `search:focus`, `profile:enter`, `profile:new`, `picker:show`) and who handles them are listed in `core/bus.ts`.
5. Backend calls: declare your commands and events by merging `interface Commands` / `interface BackendEvents`
   in `core/api` (see `features/terminals/index.ts`), then `call("cmd", args)` (never throws; returns a Result
   and toasts the error unless `{ quiet: true }`) and `listen("event", fn)`.
6. Settings: `settings()` reads, `updateSettings(patch)` saves top-level keys (unknown keys are kept, so a
   feature may store its own).
7. Commands and keys: `registerCommand({ id, title, run, enabled })` and `registerShortcut({ id, keys })`.
   Ids are `<area>:<action>` with a colon; the native menu ids in `os/menu.rs` are the contract.
   Keys use `CmdOrCtrl+X` syntax; see `core/keyboard.ts` for the input/terminal rules.
8. Styles: one css file per feature imported by its code, classes prefixed (`sb-` sidebar, `ses-` sessions,
   `search-` search, `term-` terminals, `live-` live, `git-` git, `use-` usage, `prof-` profiles, `set-`
   settings, `os-` os, `upd-` updater). Colours only from `styles/tokens.css` variables.
9. Icons: `icons`/`icon(name)` from `core/icons.ts` (incl. copy, fork, gear, file, history, undo, stash,
   commit, bell, external). `button`, `splitButton` and menu items also take an element (`IconSpec`), so an
   icon only you use stays in your folder.
10. Lists and tables: `ui/list.ts` (`createList`) virtualizes rows and owns selection and keyboard; a table
    (WP5) renders its sticky header outside `list.el`.
11. Clickable things in `#titlebar` or `#tabstrip-slot` must be `<button>`s (drag-region rule, README).
12. Imports between features: only another feature's `api.ts`. Tests: `*.test.ts` next to the code
    (vitest + happy-dom).

## 7. Safety rules for testing on the owner's workstation

- Change files only inside this repository. `ClaudeManager.ps1`, `MacUI.cs` and `%APPDATA%\ClaudeManager`
  are read-only references (a test may copy the legacy settings file to a temp folder and read the copy).
- `~/.claude` and every `~/.claude-*` folder are read-only: never create, edit, move or delete anything
  there. Tests build profiles and transcripts in `tempfile::tempdir()` (Rust) or plain objects (vitest).
- Never print or log credentials or tokens, not even in test output.
- Never kill a process you did not start. The owner runs a `pwsh.exe` window titled "Claude Sessions" and
  their own `claude.exe` sessions. A test that spawns processes ends exactly those (keep the `Child`, use
  its pid). After a GUI smoke test, stop only the `claude-manager.exe` you launched and the vite `node`
  process whose command line contains this repository's path.
- In a GUI smoke test, never type into a terminal tab that runs claude; close any you opened.
- No writes to the real registry (WP9 tests build key paths and command strings, no registry calls), no
  system-wide installs, no changes to global git, shell or system config, no push or publish, no keys or
  secrets generated or committed.
- Commits carry no `Co-Authored-By` trailer.
